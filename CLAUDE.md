# StayClean — notes for Claude

- Schema changes: edit `prisma/schema.prisma` **and** `prisma/schema.postgres.prisma` together, then `db push` (SQLite locally, Postgres via Railway boot). There is no `prisma/migrations` folder and no `prisma migrate` in this repo — `db push --accept-data-loss` is the real, documented workflow (see `scripts/railway-boot.sh`); don't introduce a migrate-based flow without checking that first.
- Never point two services' `DATABASE_URL` at the same Postgres instance — a `db push` from one branch can silently drop a column the other just added (see the incident note in `scripts/railway-boot.sh`).
- House policy numbers (thresholds, per-room-type credits, etc.) belong in the `Setting` table via `src/lib/settings.ts` (code default + DB override), never hardcoded in a component — see `getPriorityWeights`/`getRoomTypeCredits` for the pattern.
- Reuse `FloorPlanGrid`/`RoomFlagIcons`/`roomDayCategory` for anything grundriss- or day-status-related instead of re-deriving colours/icons; `/floor-plan` (reference) and the Planungshub's `PlanningFloorPlanPanel` share these on purpose.
- `requireRole([...])` in `src/lib/rbac.ts` always also passes `duty_manager` — it's the admin role. Don't re-list it.
- Guest screen lives under `src/app/g/...` (own layout, no AppShell/session), API under `/api/guest/*` only — keep both isolated from Hub screens. API + interface documented in `docs/guest-api.md`; keep it current, it's the contract for anyone building the guest frontend independently.
- Guest "current stay" resolves through the `Stay` model (`prisma/schema.prisma`), not `Arrival` — `Arrival` is a front-office event log, `Stay` carries token/date identity that must outlive check-in.
- Guest access is always via `Room.guestAccessCode` (`/g/r/...`) or `Stay.stayToken` (`/g/s/...`) — never the plain room number in a URL. Both resolve through `src/lib/guestServer.ts`; a new guest action goes in `src/lib/guestActions.ts` so it's shared by both access paths automatically.
- In a vitest file with `vi.fn()` mocks that throw/reject, reset mocks inline at the top of each `it()`, not in a shared `beforeEach` — a `beforeEach` between a throwing test and the next one can make Vitest misattribute a stray unhandled-rejection failure to the wrong (already-passing) test.
- Guest screen has its own i18n (`src/lib/guestI18n/`) and its own Modal (`src/components/guest/GuestModal.tsx`) — never reuse the staff Hub's `useLocale`/`Modal`/ivory-gold tokens on a guest page, and never subscribe a guest page to the Socket.IO broadcast (`useSocket`/`broadcast()`): it carries full unauthenticated staff payloads (names, other rooms). Guest live updates poll a narrow `/status` endpoint instead (`src/lib/guestStatusFeed.ts`).
- Guest write actions that only ever raised a `Notification` (dnd/clean-request/contact) also write a `GuestRequest` row so the guest screen has something to show a status for — see `src/lib/guestActions.ts`. `Defect`/`RoomNote` already have their own status and don't need one.
- Guest DND (`GuestRequest` kind `DND`, RECEIVED/IN_PROGRESS) never touches `Room.status`/`blockReason` — it's a separate signal, checked directly wherever it matters: `guestDndActive` on `/api/rooms` rooms (floor plan/board icons), and a dedicated gate in `applyStatusChange.ts` that blocks only `room_attendant` from DIRTY/PICKUP → IN_PROGRESS (supervisor/duty_manager pass through untouched).
- `computePriority()` takes an optional `guestCleanRequest` signal (Prompt G2 Teil 4) — wired in from `GuestRequest` kind `CLEAN_REQUEST` by `/api/priority/route.ts`. Any new caller of `computePriority` that skips this silently drops a live "guest asked for cleaning" signal.
- Supervisor manages guest requests (assign/status) at `/supervisor/guest-requests` via `GET`/`PATCH /api/guest-requests(/[id])` — the guest's own status feed (`src/lib/guestStatusFeed.ts`) just reads `GuestRequest.status`, so a PATCH here is what the guest sees on their next poll. No separate "notify the guest" step needed.
- Defect photos live under the private `./uploads` directory, never `public/` — the only way to read one is the gated `GET /api/uploads/[...path]` route (`requireAuth()`). `Defect.photoPath` is stored as `/api/uploads/<file>`; don't write photos to `public/uploads` again, that was the pre-DSGVO-fix state.
- DSGVO retention (`src/lib/guestDataRetention.ts`, run hourly by `server.js`'s ticker via `/api/internal/guest-data-retention`, same pattern as the escalation ticker) purges closed `GuestRequest` rows, guest-reported `Defect` photos, and guest-authored `RoomNote`s once past `Setting.guestDataRetentionDays` (default 30) — but only ones already closed/DONE, never anything still open. A new guest-data type that should also expire needs its own clause there; it won't be swept up automatically.
- Das Hotel hat 145 Zimmer (`Setting` `roomInventory`, Standard in `DEFAULT_SETTINGS`); `HOTEL`/Seed (139) sind nur die digitalisierten Grundrisse — für Opera-Zahlen (Forecast-Auslastung) immer `roomInventory` nehmen.
- Opera-Import (`src/lib/import/`, `docs/opera-import.md`): Parser geben nur Whitelist-Felder zurück (keine Karten-/Preis-/Saldo-/Conf-No.-Werte, auch nicht in `ImportIssue.message`); neue Spalte = bewusst in `types.ts` aufnehmen, sonst bleibt sie verworfen. Tests nur mit erfundenen Namen und selbstgebauten PDFs (`tests/fixtures/opera/`, `npm run fixtures:opera`).
- Mehrdeutige Datumswerte (Tag und Monat ≤ 12, kein Wochentag) werden nie geraten: `DATE_AMBIGUOUS` ist kritisch, bis der Nutzer eine Lesart bestätigt (`confirmedDateFormat`). Geschäftsdatum der Arrivals = Anreisetag der Liste, nicht das Druckdatum.
- `ImportBatch`-Nachimport (gleicher Typ + Geschäftsdatum) ersetzt den vorherigen Stand in `applyBatch`; kritische Befunde blockieren das Übernehmen serverseitig, nicht nur in der UI.
- Tagesplan aus dem Import (`src/lib/dayplan/`): `mergeDay` füllt `Stay`/`Trace`/`DayRoomPlan`, `applyDayPlanToBoard` (läuft automatisch in `POST /api/dayplan/merge`) schreibt `isCheckoutToday`/`occupancy`/`Arrival(source=IMPORT)`/`lastLinenChangeAt` und den morgendlichen Zimmerstatus (`boardStatus.ts`: alle sauber = INSPECTED, nur nachweislich belegte/belegt gewesene DIRTY; heute schon bearbeitete Zimmer, OUT_OF_ORDER/OUT_OF_SERVICE bleiben; Marker `Setting boardInit:<Tag>`) — nie `assignedToId`; Zimmer ohne Tagesplan-Eintrag: keine Abreise, belegt nur laut INHOUSE-Liste. Arten heißen wie in `roomDayCategory` (`DEPARTURE`, nicht „CHECKOUT"). Stay.guestName = nur „Anrede Nachname".
- Nachtlöschung (`src/lib/guestDataPurge.ts`, `docs/datenschutz-loeschkonzept.md`): jede neue Tabelle/Spalte mit Gastnamen oder Freitext braucht eine Regel in `purgeGuestDataNow` UND einen Treffer im Scan-Test (`tests/guestDataPurge.integration.test.ts` liest alle Tabellen). Der Aufruf der Löschung ist nur mit `INTERNAL_TICKER_SECRET` oder als Duty Manager möglich — nicht den schwachen `x-internal-ticker`-Header dafür nutzen.
- `Trace.dedupeKey` ist ein HMAC (`h1:…`, `src/lib/dayplan/traceKey.ts`), nie Klartext; `Trace.text` darf nach der Nachtlöschung leer sein, `mergeDay` füllt ihn beim nächsten Import wieder. `mergeDay` rechnet nie mit gelöschten (leeren) Import-Zeilen weiter.
- Neue AuditLog-Einträge: keine Namen/Freitext in `meta` unter den Schlüsseln `guestName|name|text|note|body|message` (die Nachtlöschung entfernt sie).
- Zuteilungsvorschlag (`src/lib/autoplan/`, `docs/autoplan.md`): reine Engine (`cost.ts`/`propose.ts`/`redistribute.ts`) ohne DB, client-sicher; DB nur in `load.ts`/`service.ts`. Harte Regeln (Stufe 1 nie anspruchsvoll, feste/begonnene Zimmer) sind Filter, keine Gewichte; Gewichte stehen in `weights.ts` + Setting `autoplanWeight.<name>`. Bestimmend ist `Room.assignedOn === heute`: nur eine heutige Zuteilung ist fest — jeder neue Weg, `assignedToId` zu setzen, muss `assignedOn` mitsetzen (`berlinDate`).
- `User.hkType/hkLevel/homeFloors/dailyTarget` sind Beschäftigtendaten: nur in Dateien hinter `requireRole(["supervisor"])` (Allow-List in `tests/autoplan/privacy.test.ts`), nie in Hub-Antworten, nie in `AuditLog.meta` oder `Notification.message`. Umverteilung bewegt nie begonnene Zimmer und erst nach Bestätigung (`decideSuggestion`).
- Planungstool (`/planung`, `src/components/planung/`, `src/lib/planung/`): Haus-Kacheln und Etagenbalken kommen nur aus `getHouseData()` (`DayRoomPlan`, eine gemeinsame Abfrage) — nie eigene Zimmerzählung in einer Komponente; Zimmer 145 = `roomInventory`, Kacheln nur die digitalisierten Grundrisse. Keine Gastnamen im Haus-Bild (Kachel-Info = Zimmer + Art + VIP/Wäsche/ETA).

Nach „Listen übernehmen" läuft `POST /api/dayplan/merge` automatisch; der Merge sendet `dayplan:updated {date, changedRooms}` (Live-Update + Hervorhebung nur bei Nachimport).

- Stufe/Typ von Zimmermädchen nie in `HouseData`/Planungstool-Antworten für Housekeeper sichtbar; `/planung` ist nur `supervisor`/`duty_manager`. Kachel-Gruppe hat einen Tab-Stopp (Pfeiltasten) — nicht wieder pro Kachel `tabIndex=0`.
- Planungstool Schritte 2–4 (`TeamStep`/`FloorStep`/`PlanStep`, `usePlanungFlow.ts`, reine Logik `src/lib/planung/team.ts`, DB `teamData.ts`): „heute anwesend" = `User.absentDate` der Housekeeper (Roster) + `Setting` `planningTeam` (nur IDs, Vorbelegung vom Vortag); Etagen schreiben in `User.assignedFloors` (jede Etage braucht einen *gewählten* Supervisor, nicht gewählte verlieren ihre Etagen). `/api/planung/team|floors` nur `requireRole(["supervisor"])` — Typ/Stufe kommen nur dort heraus; neue Dateien mit `hkType`/`hkLevel` in die Allow-List von `tests/autoplan/privacy.test.ts`.
- „Plan erstellen" schaltet nichts live: Entwurf ansehen/bearbeiten (`PlanEditorWindow` = `PlanningFloorPlanPanel` im Entwurfsmodus) und „Plan prüfen und bestätigen" (`PlanConfirmDialog` → `confirmProposal`) passieren im Planungstool selbst.
- Mobil (< 768 px) ist die helle Variante C derselben Tokens (Override in `.planung-root` in `globals.css`, Hauptbutton `bg-btn`, Messing-Text `text-brass-ink`); ab 768 px gilt die dunkle Desktop-Aufteilung. Playwright-Screenshots nie in den überwachten Projektordner schreiben, solange `npm run dev` läuft (Hot-Reload bricht laufende API-Aufrufe ab).
- Arbeitslisten (`src/lib/lists/`, `/api/lists/{housekeeper,supervisor,houseman}`, `docs/listen.md`): eine Quelle `loadRoomRows` (DayRoomPlan + Stay + Trace) — keine eigene Zimmer-/Gast-/Credit-Logik in Komponenten. Gast immer über `shortGuestName()` („Herr Dr. Krüger", sonst nur Nachname; nie Vornamen/Alter); Housekeeper bekommen auch aus `/api/rooms` nur den Kurznamen.
- Housekeeper-Liste: nur eigene Zimmer und nur Traces HOUSEKEEPING. Supervisor-Liste: Etagen nur über `floorsFor()` (`?floors=` gilt nur für Duty Manager, ohne Etage leer) — nie fremde Etagen.

Meldungen sind an Personen gerichtet (`Notification.targetUserId`, `/api/notifications` filtert danach): neue/alte Kraft (nur Zimmer + Etage, keine Namen Dritter) und zuständige Supervisoren (mit Namen).
